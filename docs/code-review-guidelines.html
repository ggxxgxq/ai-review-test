代码审查规范指南

1. 代码审查目标

主要目标

  • 代码质量提升：确保代码符合项目标准和最佳实践
  • 知识共享：团队成员相互学习，提高整体技术水平
  • 缺陷发现：在代码合并前发现潜在问题和 bug
  • 架构一致性：确保代码架构和设计模式的一致性
  • 安全性检查：识别安全漏洞和风险点

2. 审查流程规范

2.1 提交前自检

✅ 提交前检查清单

  • 代码编译通过，无语法错误
  • 单元测试全部通过
  • 代码格式化符合项目规范
  • 提交信息清晰明确
  • 功能测试完成

2.2 审查者选择

审查者要求

  • 技术能力：具备相关技术栈经验
  • 项目熟悉度：了解项目架构和业务逻辑
  • 时间安排：能够在 24 小时内完成审查
  • 最少审查者：至少 1 人，重要功能需要 2 人

2.3 审查时间要求

时间规范

  • 响应时间：审查者应在 4 小时内开始审查
  • 完成时间：普通 PR 应在 24 小时内完成审查
  • 紧急情况：生产问题修复应在 2 小时内完成
  • 大型变更：超过 500 行的变更可延长至 48 小时

3. 代码质量检查

3.1 功能正确性 高优先级

检查要点

  • 功能实现是否符合需求
  • 边界条件处理是否正确
  • 异常情况处理是否完善
  • 业务逻辑是否合理

✅ 正确示例

function calculateDiscount(price: number, userType: string): number {
  if (price <= 0) {
    throw new Error('Price must be positive');
  }
  
  if (!userType || !['premium', 'regular', 'vip'].includes(userType)) {
    throw new Error('Invalid user type');
  }
  
  const discountRates = {
    premium: 0.15,
    regular: 0.05,
    vip: 0.25
  };
  
  return price * discountRates[userType];
}

❌ 错误示例

function calculateDiscount(price, userType) {
  return price * 0.1; // 硬编码折扣率，没有验证输入
}

3.2 代码可读性 中优先级

检查要点

  • 变量和函数命名是否清晰
  • 代码结构是否合理
  • 注释是否充分且准确
  • 代码复杂度是否适中

✅ 正确示例

/**
 * 计算用户订单总金额
 * @param items 订单商品列表
 * @param discountRate 折扣率 (0-1)
 * @returns 计算后的总金额
 */
function calculateOrderTotal(items: OrderItem[], discountRate: number): number {
  const subtotal = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
  const discount = subtotal * discountRate;
  return subtotal - discount;
}

❌ 错误示例

function calc(a, b, c) {
  return a.reduce((x, y) => x + y.price * y.qty, 0) - a.reduce((x, y) => x + y.price * y.qty, 0) * b;
}

3.3 性能优化 中优先级

检查要点

  • 是否存在性能瓶颈
  • 数据库查询是否优化
  • 内存使用是否合理
  • 算法复杂度是否可接受

✅ 正确示例

// 使用 Map 提高查找效率
const userCache = new Map();

function getUserById(id: string): User | null {
  if (userCache.has(id)) {
    return userCache.get(id);
  }
  
  const user = fetchUserFromDatabase(id);
  if (user) {
    userCache.set(id, user);
  }
  return user;
}

❌ 错误示例

// 每次都查询数据库
function getUserById(id: string): User | null {
  return fetchUserFromDatabase(id); // 没有缓存，性能差
}

3.4 安全性检查 高优先级

检查要点

  • 输入验证是否充分
  • SQL 注入防护
  • XSS 攻击防护
  • 敏感信息泄露
  • 权限控制是否完善

✅ 正确示例

// 使用参数化查询防止 SQL 注入
async function getUserByEmail(email: string): Promise {
  // 验证邮箱格式
  if (!isValidEmail(email)) {
    throw new Error('Invalid email format');
  }
  
  const query = 'SELECT * FROM users WHERE email = ?';
  const result = await db.query(query, [email]);
  return result[0] || null;
}

❌ 错误示例

// 存在 SQL 注入风险
async function getUserByEmail(email: string): Promise {
  const query = `SELECT * FROM users WHERE email = '${email}'`;
  const result = await db.query(query);
  return result[0] || null;
}

4. 代码风格检查

4.1 命名规范

命名要求

  • 变量：使用驼峰命名法 (camelCase)
  • 常量：使用大写下划线 (UPPER_SNAKE_CASE)
  • 函数：使用动词开头，驼峰命名法
  • 类：使用帕斯卡命名法 (PascalCase)

✅ 正确示例

const MAX_RETRY_COUNT = 3;
const API_BASE_URL = 'https://api.example.com';

class UserService {
  async getUserById(userId: string): Promise {
    const userData = await this.fetchUserData(userId);
    return this.transformUserData(userData);
  }
}

❌ 错误示例

const maxRetryCount = 3; // 常量应该用大写
const apiBaseUrl = 'https://api.example.com';

class userService { // 类名应该用帕斯卡命名法
  async getUserById(user_id: string): Promise { // 参数应该用驼峰命名法
    const user_data = await this.fetchUserData(user_id);
    return this.transformUserData(user_data);
  }
}

4.2 代码格式

格式要求

  • 使用 2 个空格缩进
  • 运算符前后要有空格
  • 行末不允许有空格
  • 文件末尾必须有换行符

5. 测试覆盖检查

5.1 单元测试 高优先级

测试要求

  • 新功能必须有对应的单元测试
  • 测试覆盖率不低于 80%
  • 测试用例要覆盖正常和异常情况
  • 测试名称要清晰描述测试场景

✅ 正确示例

describe('UserService', () => {
  describe('getUserById', () => {
    it('should return user when valid id is provided', async () => {
      // Arrange
      const userId = '123';
      const expectedUser = { id: '123', name: 'John Doe' };
      jest.spyOn(userService, 'fetchUserData').mockResolvedValue(expectedUser);
      
      // Act
      const result = await userService.getUserById(userId);
      
      // Assert
      expect(result).toEqual(expectedUser);
      expect(userService.fetchUserData).toHaveBeenCalledWith(userId);
    });
    
    it('should throw error when invalid id is provided', async () => {
      // Arrange
      const invalidId = '';
      
      // Act & Assert
      await expect(userService.getUserById(invalidId))
        .rejects
        .toThrow('Invalid user ID');
    });
  });
});

5.2 集成测试

集成测试要求

  • API 接口要有集成测试
  • 数据库操作要有集成测试
  • 第三方服务调用要有集成测试
  • 测试环境要与生产环境隔离

6. 文档和注释检查

6.1 代码注释

注释要求

  • 复杂业务逻辑必须有注释
  • 函数要有 JSDoc 注释
  • 注释要与代码保持同步
  • 避免无意义的注释

✅ 正确示例

/**
 * 计算订单折扣金额
 * @param orderTotal 订单总金额
 * @param userLevel 用户等级 (bronze, silver, gold, platinum)
 * @param couponCode 优惠券代码 (可选)
 * @returns 折扣金额
 */
function calculateDiscount(
  orderTotal: number, 
  userLevel: UserLevel, 
  couponCode?: string
): number {
  // 基础折扣率根据用户等级确定
  const baseDiscountRate = getUserLevelDiscountRate(userLevel);
  
  // 如果有优惠券，应用额外折扣
  const couponDiscount = couponCode ? getCouponDiscount(couponCode) : 0;
  
  // 计算最终折扣金额
  return orderTotal * (baseDiscountRate + couponDiscount);
}

6.2 API 文档

API 文档要求

  • 新增 API 要更新文档
  • 参数和返回值要详细说明
  • 提供请求和响应示例
  • 错误码要有说明

7. 审查反馈规范

7.1 反馈类型

反馈分类

  • 必须修改：影响功能、安全或性能的问题
  • 建议修改：代码质量和可维护性问题
  • 可选修改：代码风格和个人偏好问题
  • 问题讨论：需要进一步讨论的技术问题

7.2 反馈格式

反馈要求

  • 反馈要具体明确，避免模糊表述
  • 提供修改建议或示例代码
  • 解释问题的原因和影响
  • 使用礼貌和建设性的语言

✅ 好的反馈示例

建议修改：这个函数缺少输入验证，可能导致运行时错误。

建议添加参数验证：
```typescript
function processUserData(userData: any) {
  if (!userData || typeof userData !== 'object') {
    throw new Error('Invalid user data');
  }
  // ... 其他逻辑
}
```

这样可以提高代码的健壮性，避免潜在的空指针异常。

❌ 不好的反馈示例

这个函数有问题，需要修改。

代码写得不好。

应该用更好的方式实现。

10. 审查最佳实践

审查者最佳实践

  • 及时响应：在承诺时间内完成审查
  • 建设性反馈：提供具体的改进建议
  • 学习态度：保持开放和学习的心态
  • 平衡检查：既关注细节也关注整体架构

被审查者最佳实践

  • 充分准备：提交前进行自检
  • 积极回应：及时回复审查意见
  • 持续改进：从审查中学习和改进
  • 保持沟通：对不清楚的意见主动询问

团队最佳实践

  • 轮换审查：避免总是同一个人审查
  • 知识分享：定期分享审查经验和技巧
  • 工具集成：将审查工具集成到开发流程
  • 持续改进：定期回顾和优化审查流程
